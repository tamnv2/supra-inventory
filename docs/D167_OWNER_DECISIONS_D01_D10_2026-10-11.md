## 2. End-to-end contracts required in next CODE READY

Template columns (only required business fields): `Mã nhân viên`, `Họ và tên`, `Nhà thầu`; .xlsx (the source must be normalized and validated before applying). Require a valid normalized employee code, non-empty name and contractor; reject bad format or missing columns/rows with 1-based Excel row references. Note existing `normalizeHrEmployees` in `service/src/user-management-core.ts` currently allows empty `contractor_name`; the new rule must change before activation.
- One shared preview/commit API for manual entry and Excel. Duplicate same code and identical normalized fields: `UNCHANGED`; different name or contractor within uploaded file: `FILE_CONFLICT` (block until corrected); existing Picker same code with changed name/vendor: `CHANGE_REQUIRES_EXPLICIT_CONFIRM`; code colliding with Root/Admin/Reporter/non-Picker: **BLOCK**, no privilege/role takeover; empty/invalid rows: **BLOCK**; new Picker: `CREATE` with reporting **enabled**. Rows missing from uploaded Excel: **NO DISABLE/NO DELETE**; existing inactive user: do not auto-reactivate. Idempotent request_id/source fingerprint, CAS/source-readback preflight and an auditable human acknowledgment of proposed rename/vendor update. Proposed default is **all-or-nothing per validated commit**, not silent partial import; batch transaction/limits and large Excel size must be tested.
- Preserve existing Firebase auth/account password setup, role protection, existing manual disabled reporting preference, prior login/ACK and any HR records. Disable/retire the `Drive Watch` and cron HR sync **only after** Web source migration end-to-end passes Beta and scoped Owner deploy approval; no direct deletion of the old GSheet or other services' Sheets. Old source and stale UI labels remain marked LEGACY until code changed; this document alone does not disable them.

### D03+D04: shared VN business-day batch invariant (must be one migration/test group)
- Each `batch` has immutable `business_day_vn` from first report date (not the result time), canonical time source InventoryCore VN. A SKU may have **one PENDING batch per VN business day**, multiple PENDING batches across different days. Replace incompatible `idx_pending_batch_sku ON report_batches(sku) WHERE status='PENDING'` with protected transactional per-day uniqueness **after migration/preflight**; safely handle all legacy rows and rollback; do not drop index blindly. Duplicate ticket guard is **(Picker identity, SKU, VN day)** not all open days. Concurrent new users and same Picker at 23:59/00:00 must yield one day-scoped batch, no cross-day ticket mixing.
- At **03:00 N+1**, process **all still PENDING** batches whose `business_day_vn=N`, regardless `d167_first_overdue_at`, `auto_skip_allowed_at`, active SLA setting or whether any Picker ticket has yet crossed individual auto-skip. Mark every outstanding OPEN ticket as `SKIP_ALLOWED` with `SYSTEM_DAY_END`, keep WITHDRAWN or human-resolved tickets immutable and do not change unrelated day N+1 batches. Archive event once transactionally, preserve real action time 03:00 or delayed catch-up actual timestamp separately and business N for reporting. Catch-up after outage must show actual performed_at and scheduled_for=03:00 (not fabricate 03:00 action time).
- Web/Android `SKIP_ALLOWED` shows distinct warning treatment and clear content `Hệ thống tự động cho phép Skip lúc 03:00 do Inventory chưa xử lý trong ngày`; role source `SYSTEM_DAY_END` distinct from `REPORTER` and `SYSTEM_TIMEOUT`, not falsely called `quá hạn` for non-overdue tickets. Picker delivery uses existing realtime/FCM and result ACK with exact batch_id/version/event_id and idempotency; one 03:00 batch transition produces no duplicated outcome/counter/FCM on alarm replay or HA. Live tabs show only PENDING/OVERDUE now; past day's SKIP closes into existing result-history view, not an invented historical live view.
- Test >200 pending batches, no overdue ticket, all tickets already withdrawn, partial withdrawals, one/multiple Picker, old day and new day same SKU, same Picker same SKU across midnight, old UI versions, lease/DO alarm retry, 03:00 worker restart, correction window policy if applicable.

### D07: temporal LTA/Shelving classification, not bin inventory
- Derive the **coarse area label** from the authorized export's validated location metadata only; business values `LTA`, `SHELVING`. `UNKNOWN` is an evidence-gap display state, not a third known storage area. No SKU-level quantity, exact bin, operational pickface CRUD or stock mutation enters Inventory.
- Per SKU record an immutable observed change sequence with `area`, `effective_from`, `effective_to`, `source_fingerprint`, `observed_at`, service audit, and non-overlapping validity intervals. First verifiable observation is start of known history; earlier reports must say `UNKNOWN`. Identical consecutive area ⇒ no update. New area ⇒ close prior interval and append at commit observation timestamp. A missing SKU or absent location label must **not** erase last verified interval, but views of periods outside reliable evidence must be transparently bounded; ambiguous or multi-area SKU is `UNKNOWN`/needs source-policy review, never arbitrarily choose one.
- A shortage report should bind to the verified **as-of report timestamp**, not the newest current SKU position. Reconciliation of SKU observations after report timestamp cannot fabricate an earlier effective_from. If source export lacks area/cannot classify, stop area-ingestion independently while continuing validated SKU+name; do not present a fictitious LTA/Shelving. Report summary/details/export compare exactly the same area snapshot and business date. Data retention and older-than-first-observation UNKNOWN are mandatory; no direct external/WMS lookup per report row.
