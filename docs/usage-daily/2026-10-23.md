### 6.3 Source-level risk shortlist (S) — current main

- `service/src/d166-sql-usage.ts` provides existing `d166MeasuredSqlRows()` cursor-based `rowsRead` observations with query IDs, executions, max, latency. It is **instance-isolated, in-memory, bounded, reset on DO isolate restart**; aggregate is `ESTIMATE_NOT_BILLING`. Reuse this instrumentation by authorized read-only admin path before adding monitoring requests (those would themselves cost usage).
- `service/src/operational-v2-core.ts`: `currentBatchSnapshot` uses several correlated subqueries on tickets, acknowledgements and history; `reporterCounters`, `reporterQueue`, `reporterOverdue`, `recentResults`/`RECENT_ACK_TOTALS`, `pickerReports` and `pendingResults` are explicitly instrumented.
- `RECENT_ACK_TOTALS` uses repeated `COUNT(DISTINCT)` across result acknowledgements, and `BATCH_SNAPSHOT` has many `COUNT/MIN/MAX` correlated expressions. **Optimization candidates** after `rowsRead` fingerprint attribution / `EXPLAIN QUERY PLAN` (sandbox equivalent first); never claim index omission proven from SQL text. Some index definitions and cached summary tables already exist; changing them without checking planner is unsafe.
- If read/DO request ratio tracks Reporter refresh/get path, focus `REPORTER_*` and `RECENT_*` SQL plus client realtime fallback rather than disabling FCM/WebSocket/HA. If rows read mainly batch snapshot/timer jobs, fix backend scans/overdue logic instead; A/B/C/D reducing DO request count alone may not reduce SQLite row-meter.
- Shared namespace can contain D172 specific business tables. Require role/path separation and D172 vs Báo hàng regression for every future Worker/DO change.
