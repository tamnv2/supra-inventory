## Distinguish the networks
- **Office:** Owner field-confirmed SUPRA WMS UI and selected Google endpoints; Office **cannot directly access Cloudflare Inventory host**. RTDB corporate proxy produced HTTP 403; Firestore authenticated PDA ↔ Office Agent transport had successful field proof under D091.
- **Ordinary Internet/PDA network:** existing Cloudflare and Google service path, and RTDB where network permits. **WMS reachability on ordinary Internet is not established**; never assume company WMS is publicly accessible.
- Windows Agent currently honors Windows routing/default/system proxy; no general SSID-locked routing or automatic provider-aware network adapter failover. `Program.cs` refreshes Windows proxy on network changes; `FirestoreHttpTransport.cs` uses default/system proxy; `D167SkuDirectExport.cs` uses system proxy. One PC with both adapters connected needs end-to-end route evidence, not just displayed Wi-Fi name.

## Operational implications
1. An Office-only PC can run WMS and Google/Firestore-based confirmation, but **not guaranteed feature-complete**: RTDB HA is blocked, direct Cloudflare update is blocked, and end-to-end SKU Gateway/redirect/UrlFetch has no Office field PASS.
2. An Internet/PDA-only PC can access Cloudflare/Google/RTDB but cannot be assumed capable of WMS confirm or SKU export without actual WMS access. **Do not classify all Agent features as Internet-only**.
3. A dual-network machine is not automatically a safe solution. It can select the wrong Windows adapter/proxy; preserve WMS session and token isolation. Prefer endpoint-based controlled proof rather than forcing all traffic to Office or to PDA.
4. D168 incident: 948 `D167_SKU sync=DEFER` on a PRIMARY trace (16:49–19:52 VN), no confirmed `DELTA_19 DONE`, a readiness event bypassing 15-minute cooldown, and 27 separate quota-related UrlFetch errors. Both Office and PDA Wi-Fi were seen in failing logs. Attribution to Office firewall alone is unjustified. Log upload failures on two Agents must be triaged independently, while checking shared Google Gateway quota.
5. Minimum Office-only acceptance: WMS read-only authorized export PASS; Firebase Auth/Firestore confirm ACK PASS; one no-mutation Gateway schedule/status request completes through Google response redirect; when Owner authorizes a controlled SKU publish, Worker durable `FULL/DELTA DONE` receipt and roster fingerprint match; log upload `DRIVE_SYNCED` receipt; RTDB unavailable fallback/HA scenarios tested. Verify exact interfaces and proxy outcomes without logging raw SSID, WMS credentials or tokens.

## Recommended design direction (NOT approved for code/release)
- Preserve WMS Office route and already-registered Google SKU Gateway; first repair D168-REQ-009 retry-storm and evidence/classification and D168-REQ-008 log-upload timeout/backoff independently. No new background poll or billing-bearing provider endpoint.
- Add an **observational** Agent network-capability matrix based on existing successful service responses, not Wi-Fi SSID labels; show per-feature ready/degraded/blocked/unverified. Do not infer capability from a single Auth probe or from a visible Wi-Fi name.
- Keep RTDB optional/HA-degraded Office fallback explicit; keep authoritative Firestore role/generation fencing and preserve latency/HA acceptance thresholds.
- If Google Gateway is blocked by Office or quota remains structurally inadequate, evaluate only separately Owner-approved existing Firestore/Google Function capabilities and registered resources. No new resource, Cloudflare bypass, stable change or direct-to-Sheet transaction fallback is authorized.
