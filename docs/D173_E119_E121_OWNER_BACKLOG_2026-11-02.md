**Observed code baseline:** `relay-agent/Program.cs` already implements main form `ShowInTaskbar=false`/Hide in `MinimizeToTray()`, and restores the main window with `ShowInTaskbar=true`. This does **not** establish that either observed auxiliary window is directly created by the Agent, or identify its process/window handle. The labels are consistent with Windows/.NET helper windows, but root cause is **not established** without process and HWND identification.

**Acceptance requirements (after separate code approval):**

- Do NOT enumerate and hide unrelated system/application windows or assume any window with the same title is owned by the Agent.
- Avoid side effects to WinForms message broadcasting, GDI+, NotifyIcon, WebView2, printer dialogs, actual WMS and PRIMARY/ACK/HA.

## D173-E121 — Online/offline Web presence, without INCREMENTAL usage
**Owner issue:** a Web login may remain persisted while the browser/user has disconnected or become idle. It must not continue being labeled actually “online” merely because the last login exists.

**Verified source facts:**
- `web/src/realtime-client.ts`: authenticated Web already creates a realtime WebSocket using a ticket and maintains connection/reconnection state (existing 5-second local ensure timer, not itself a provider request on every iteration).
- `service/src/read-model-core.ts`: `realtimePresence()` enumerates `state.getWebSockets()` and returns `online_sessions` and `sessions` including `client_type: WEB/ANDROID`; `agentReporterPresence()` also already joins authenticated user session rows with WebSocket evidence and exposes `connected`. This latter function explicitly distinguishes login/session registry from connection evidence.
- `web/src/operational-app.ts`: visible Admin dashboard already invokes `getRealtimePresence()` on refresh every 30 seconds; background-hidden pages skip this refresh. DO `webSocketClose` currently does NOT set Picker presence by itself; do not change Picker authority as part of Web presence.
- Existing WS hibernation auto response to a protocol-compatible `ping` string is configured server-side, but this alone does NOT prove that browsers send a ping or that abrupt network failures are immediately detected.

**Candidate with ZERO NEW provider operations (best-effort connection state, not guaranteed active-person proof):**
1. Define separate display labels: `Đã đăng nhập (phiên còn hiệu lực)`, `Đang kết nối (WebSocket đang mở)`, `Mất kết nối / không xác minh được`, and optionally `Vừa thao tác` only when an already-existing trusted business/action event supports it. Do not label idle tab as “active human”.
2. Reuse the already queried authenticated presence payload or the existing Agent roster response with `connected`, scoped to `WEB`, **without additional API/DO calls, heartbeat, Firestore writes, listeners or polling frequency**.
3. Cache/deduplicate by user+session/channel/generation; distinguish multiple browser tabs/devices, and enforce authorization so ordinary users cannot enumerate other identities. Never expose token/JWT/secret.
4. State freshness and stale/unknown explicitly: when no fresh snapshot exists, say `Chưa xác minh` instead of guessing online/offline.
5. Keep existing realtime command/event latency and Cloudflare DO request rate unchanged. Compare source-matched billed usage before and after if this is ever coded.

**Physical limitation:** Even if the already-existing socket snapshot adds **zero new requests**, a browser tab can stay connected with no human activity, and an abrupt Wi-Fi outage can leave a stale server-side socket temporarily. Instant, guaranteed, across-device true offline/person-active detection cannot be promised at zero additional signaling/processing cost. No blanket “zero usage” guarantee; explicit zero-*incremental-new-operations* criterion and existing refresh interval only.

**Next step:** source-based design and acceptance criteria for connection-vs-session-vs-activity using existing requests. Only after separate Owner approval implement in needed Web/Agent/backend components, with D172 shared Worker regression. No code, CI runtime or production change now.
