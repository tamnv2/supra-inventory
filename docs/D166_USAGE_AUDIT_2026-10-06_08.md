## C. Firestore reads 23K: phân tách nguyên nhân thực và mô hình có thể kiểm chứng

1. **Đã chứng minh bằng code:** `FirestoreAgentLeaderCoordinator.cs` refresh PRIMARY/NEXT_A role 60s, NEXT_B 120s, DEEP 600s, PRIMARY heartbeat RTDB ~10s, NEXT_A `CheckPrimaryLease()` REST Firestore khi RTDB không fresh. `FirestoreD157Realtime.cs` duy trì listener pending; `AGENT_SYNC` listener và reconcile 5m ở log. `FirestoreHttpTransport.SendJson()` có retry an toàn và `FirestoreQuotaGuard.Record()` local reference estimate; không phải thống kê billing toàn hệ thống.
2. **Đã chứng minh bằng log:** có 1,390 `QUERY_FRESH_ONLY pending=0` trong 1,453 polls, ~226 sự cố RTDB observer, ~75–76 lần mở lại Agent Sync listener, nhiều gRPC auth/stream lỗi. Các số này gợi ý read amplification, *không* đủ chứng minh tổng 23K xuất phát từ một nhánh.
3. **Lập luận tránh quy sai:** Google APIs list 54,724 **Firestore API requests** không bằng 23K **document reads**; API requests có LISTEN/RUN_QUERY/GET/PATCH/ACK, read charges theo document/minimum query và listener lifecycle. 23K có thể bị ảnh hưởng bởi nhiều Agent, Android listeners, role/presence, HA fallback, D157 pending query và retry; không thể dùng một đối chiếu log tổng để quy thuộc tiền.
4. **Candidate nguyên nhân cao #1:** `QUERY_FRESH_ONLY` làm nhiều empty query khi listeners connected. Kiểm tra `listener_connected`, `last_event_at`, `active_PDA`, `last_rest_fallback`, `trigger(reason)` bằng counters **RAM-only**; không tự ý cắt watchdog/đổi cadence. Nếu trùng lặp không có safety value, đề xuất loại đúng nhóm dư sau field replay.
5. **Candidate nguyên nhân cao #2:** RTDB stream timeout / HTTP401/403 -> recurring lease reads (và authorization retry); cần ghép generation, true startup freshness, liveness observer health với số lease GET từng giờ. Không suy ra 226 SSE lỗi = 226 reads (có thể nhiều lease reads / one incident).
6. **Candidate nguyên nhân cao #3:** Agent Sync gRPC auth/relisten -> snapshot read recharged, với nhiều Agent đồng thời; cần instrument local snapshot docs count, reconnect cause, initial/relisten cadence, not log payload.
7. **Candidate nguyên nhân #4:** presence/control docs cùng Firebase Auth token refresh hoặc legacy clients; cần Firestore API method/hour từ Provider Monitoring, đối chiếu actual Agent versions. Không giả định Web/SKU Worker traffic là Firestore business reads.

### Firestore source-level quantified floor & guard mismatch (read-only investigation 09/10)

- `FirestoreConfirmationTransport.D158DesiredPollIntervalMs()` confirms **healthy listener watchdog 10s when PDA active / 30s when inactive**; degraded listener path 1s hot / 2s bounded resilience / 3s normal / 15s inactive. `ReadPendingDocuments` POSTs Firestore `:runQuery` and calls `LogPollTelemetry("QUERY_FRESH_ONLY",...)`, so 1,453 observed `QUERY_FRESH_ONLY` events represent successful REST queries, not internal cache lookups.
- Of these, **1,390 empty successful RunQuery replies**. If each empty query is billed the Firestore minimum document read (official billing rule), that group alone accounts for **at least ~1,390 reads (~6% of the 23K total)** during the covered window; this is a minimum conditional estimate, not the full billed attribution. It does **not** explain the additional 8K reads versus 06/10 without knowing 06/10 empty-query baseline and other listeners. Reconnect, multi-document queries and separate callers require method-level provider proof.
- `FirestoreQuotaGuard.ReferenceReadsPerDay=50000`, `SoftReadsPerDay=45000`, `AllowOptionalFastPath` permits until process-local **40K**. This is **per Agent process reference accounting**, while project D165 target is <=10K/day total (prefer <=8K) with potentially multiple Agent processes. Therefore **current local guard thresholds cannot enforce the cross-Agent target**, and an Agent may appear locally under budget while provider project reads exceed target. The right next action is cross-agent evidence aggregation and a safe approved budget strategy, NOT a new polling quota controller.
- `FirestoreHttpTransport` calls `FirestoreQuotaGuard.Record` before each attempted REST call; `RecordReadDocuments` adds extra docs beyond the first returned document. This is *locally estimated* operation cost; Firestore SDK listeners, metadata reads/index entry charges, other Agent/PDA clients and query retry semantics are not completely captured. v123 instruments existing attempts and measured outcomes separately.
- **Priority for 09/10 investigation:** partition provider reads into REST successful empty query, REST positive query, gRPC initial snapshot/relisten, HA role/lease GET, Agent presence/reconcile, Android app listeners and writes; sort by exact active Agent-hour and Picklist-hour, not total cumulative.
- **Potential repair after Owner approval:** avoid unnecessary REST watchdog when its independent safety value can be disproved under tested stale-stream scenarios; fix SSE RTDB readiness/lease handoff; never delete fallback merely to hit quota. Candidate optimization impact must include 15s failover, WMS mutation safety and ACK delivery. This report does not authorize code changes.
